Design baseline: `round6-validation`, `dffb65fca2462698d7664f5af82b70971a39a1c6`, 2026-10-25. Minecraft Fabric 26.3 Vulkan, Streamline 2.14.16, RTX 5070, Ryzen 7800X3D, driver 617.42. This document is a plan, not a runtime validation report. No mod source was changed and no game, build or benchmark was run while preparing it.

Ryan expanded this task to include larger defects anywhere in rendering, FG, Reflex, presentation and CPU work. The ranked work below includes those candidates. `DLSS_COST_PLAN.md` remains the record of the earlier bounded copy-removal task; this document does not retroactively authorize its worker to change defaults, fences or frames in flight.

## Verdict and numerical budget

There is useful work left. The most certain speed choice is CNN instead of Transformer, and the first integration result needed is the saving from the local-tag change already in `dffb65f`. Neither supports a promise that enabled DLSS will always beat native in lightweight scenes. That promise becomes physically impossible when the critical-path evaluation plus required extra work exceeds the pixel work actually removed and there is no independent work with which to overlap it. Whether this particular integration has reached that limit is still unproven.

Established evidence, preserved without rerunning it:

- Round 10 Quality evaluation, 1280x720 render input to 1920x1080 output: CNN E 0.264 ms, Transformer K 0.628 ms, a 0.364 ms difference. NVIDIA's supplied RTX 5070 guide figures are CNN 0.27/0.43/0.93 ms and Transformer 0.64/1.02/2.11 ms at 1080p/1440p/4K output. These are evaluation costs, not predicted whole-frame gains for every scene.
- Tonight's `762cadc` moving route, 1920x1080, Mellow, DH rendering on and generation off: native 403.5 FPS; CNN Quality 382.7; Transformer Quality 337.4. These are single valid passes, not accepted repeat pairs. Native/CNN/Transformer 1% lows were 206.7/220.0/204.9 and 0.1% lows 126.2/147.4/137.0. Do not claim a repeatable tail improvement from them.
- Numerical provenance issue: the brief also reports +0.27/+0.67 ms per frame for those rows. Reciprocal FPS gives 2.478/2.613/2.964 ms, hence +0.135/+0.486 ms relative to native and a 0.351 ms CNN advantage over Transformer. Preserve the reported deltas as unpaired timing figures until their raw metric/window is identified. Do not add them to the reciprocal means or silently substitute them.
- Round 17 GPU accounting: native world 0.956 ms, Quality world 1.384 ms, evaluation about 0.588 ms. Removing evaluation from that accounting gives only about 0.161 ms net saving in the remaining world work. The task separately supplies about 0.260 ms for light-pack terrain/deferred/composite/final work savings; that pass-level estimate cannot be equated with the net world delta or added as a separate gain. Do not combine this pose, resolution or profiler window with tonight's moving route. Round 16's 1440p evaluation was 0.932 ms; its older minimal/DH-off FPS rows are not content-validated proof of a defect.
- On 23 Oct, raw NGX CNN already gave BSL +25% Quality/+44% Performance and Complementary +24%/+44%, but Mellow -9%/-3% at about 825 FPS. This is evidence of workload-dependent crossover, not proof that Streamline overhead is zero.

For a GPU-limited frame, reason about `extra GPU time = evaluation + extra passes/copies/synchronization - work removed by lower render resolution`. In a pipelined CPU-limited frame, only the added critical path matters. Completion waits can expose GPU cost to the CPU; their duration must not be added again to the GPU work they wait for. Reducing CPU allocations cannot recover GPU time on a GPU-limited frame.

At tonight's reciprocal means, CNN needs roughly 0.135 ms more saving to tie native; Transformer needs roughly 0.486 ms. Local tags and a real pass defect could plausibly close the CNN gap, but there is no measured budget proving they will. Keep the original, separately reported +0.27/+0.67 ms figures visible in the final report until reconciled. No numeric shaderless gain is established by these Mellow rows.

All saving ranges below, except the model comparison, are **provisional engineering budgets**, not measurements or confidence intervals. Zero is a valid result. They refer to 1080p on this hardware, and are not additive: barriers, copies, waits and CPU/GPU overlap can describe the same elapsed time. A newly found pass is budgeted from its own timestamp before implementation, not from its resolution alone.

### 2. Validate local tags, including the FG history exception

Change: first measure the existing fix, not another rewrite. If a trace proves residual SR copies after FG use, audit each resource's actual lifetime. Where it really survives unchanged through present, pass a truthful `eValidUntilPresent` local tag so preprocessing skips a temporary copy; retain separate FG global tags. Otherwise change producer/lifetime ownership narrowly. Never relabel a reused image as long-lived merely to bypass copying, patch SDK internals, or invent separate viewport identities without checking shared constants/feature contracts.

Expected saving: **0 to 0.10 ms/frame** as a provisional budget for removing the two old input copies and associated barriers. **0 additional** if `dffb65f` already removed them. Residual post-FG savings are included in this budget, not another 0.10 ms.

Verification: one old/new same-preset evaluate A/B with a one-frame API trace proving which color/motion copies disappeared. Add a short lifecycle sequence in the same diagnostic: fresh SR-only, FG enabled, FG disabled back to SR. Count copies at each state. An empty clone log is not proof. A trace establishes copy absence; profiler deltas establish time. Risk: premature reuse, stale tags or FG corruption; check a 20-second fixed-2x sequence with a camera turn, rising generated counters and no new artifacts/errors. Stop after one patch attempt and one correction; if safety cannot be proved, keep the safe lifecycle and report the remaining cost. Haiku gathers traces; DeepSeek owns any lifetime change.

## What shipped games establish, and what they do not

NVIDIA's historical [Rainbow Six Siege DLSS announcement](https://www.nvidia.com/en-us/geforce/news/gfecnt/20216/rainbow-six-siege-nvidia-dlss-out-now/) advertised the Vulkan integration's gain at 4K with maximum settings. Ubisoft's [Vulkan renderer explanation](https://www.ubisoft.com/en-us/game/rainbow-six/siege/news-updates/6VFn74oMO2nVQGZxvFhBb5/vulkan-api-testing-on-live-pc) describes dynamic resolution targeting a chosen frame rate for GPU-bound players. These are specific shipped-engine strategies for scaling expensive pixel work, not evidence of universal SR gains at 400 to 800 FPS. NVIDIA's [early DLSS FAQ](https://www.nvidia.com/en-sg/geforce/news/nvidia-dlss-your-questions-answered/) explicitly warned that high FPS/low resolution may not gain; it is historical context, not a prescription for the current runtime or permission to copy old availability restrictions.

For Reflexium, offer truthful native/DLSS choices and measure real GPU headroom. Do not import a dynamic-resolution controller or model threshold merely because another engine has one. At 400 FPS, a 0.264-ms evaluation is about 11% of the 2.5-ms frame budget; at 800 FPS it is about 21%, before any savings or overlap. A shipped game can hide part of that cost behind useful independent work, amortize it against expensive shading, or let the user choose native. None makes the evaluation free.

The pinned FG guide (`native/streamline/ProgrammingGuideDLSS_G.md:805`) also describes host-present blocking reductions in its example. This is a reason to inspect presentation timelines, not a promise of a 1-ms saving on this Vulkan implementation. Report real FPS, generated presents and PCL latency separately.

## Explicit non-actions and completion gates

- Do not revive raw NGX as the shipping fix. A historical same-build raw-NGX/Streamline diagnostic can isolate overhead if still needed under the earlier cost plan, but comparing unrelated commits as if only the API changed is not causal evidence.
- Do not disable jitter or object motion, reduce shadows/DH distance, remove post effects, sharpen away softness or turn SR off while reporting a DLSS gain. Do not use MFG output FPS to certify SR performance.
- Do not restore the blanket DLSS-G transition-error allowance. `FrameGenerationRenderer.java:795` deliberately stops on nonzero status, and round 10 removed the prior allowance. Investigate an observed status by its exact SDK meaning; an unmeasured claim that it is transient is insufficient.
- Do not add a deprecated PCL InputSample marker because a generic checklist requests it: `native/streamline/include/sl_pcl.h:68` explicitly deprecates that enum. Keep the version-matched Vulkan marker mapping unless contrary evidence appears.
- Do not rewrite the renderer, introduce a frame graph, or increase frames in flight for a speculative saving. One hot spot, one bounded A/B, one decision. If a gate fails, proceed to the next item rather than starting a new validation round.
- Final implementation handoff lists retained patches, rejected hypotheses, per-item old/new microseconds and limits, exact artifact hashes, image/latency regressions and unverified objectives. Run the one final route/CapFrameX batch only after retained patches are integrated. A no-gain result is a completed experiment, not permission for unlimited retries.

This plan does not declare the release objectives met. It identifies source-backed work, conditional experiments and quality defects separately, and leaves final speed/quality claims to matched measurements.
