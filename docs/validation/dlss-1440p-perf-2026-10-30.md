## Expected-gain model and discriminator

For a serialized diagnostic approximation, in milliseconds:

```
t_native = N + S + P_native
t_dlss(r) = N + r*S + E(model, output, input) + P_dlss + H
r = render_pixels / display_pixels
gain_percent = 100 * (t_native / t_dlss - 1)
```

N includes shadow maps, geometry and any CPU critical-path work that does not shrink with viewport.
S is the resolution-dependent share at native. E is evaluation; P is display-resolution work;
H is additional integration work not already inside the other spans. In a pipelined engine use
the maximum of CPU and GPU critical paths plus non-overlapped waits, rather than adding CPU and
GPU durations indiscriminately. Completion waits overlap GPU work and are not a second GPU charge.

Quality r is about 4/9, Balanced about 0.3364 (verify actual SDK extent), Performance 1/4,
Ultra Performance about 1/9. Even ignoring H and extra display work, Quality with E=1.02 ms
needs more than 1.836 ms of native resolution-dependent work to break even. This is arithmetic
using the guide's K reference budget, not a measured Quality threshold on this client.
With N=0 as an idealized bound, a 50% Quality gain needs S=4.59 ms. Any fixed N raises that
requirement. Games near tens of FPS can amortize a millisecond much more easily than a light
Minecraft scene near hundreds of FPS.

Discriminating test, still unperformed:
