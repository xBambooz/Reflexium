## Hand: partly fixed

### Discriminating evidence

Range pose `(200.5,151,0.5)`, yaw 0, pitch 3. Baseline pack and shaderless captures exist for native, Ultra Performance and Quality. `hand-before-sequence.json` and `hand-force-sequence.json` record a 15-degree pan. Both initially submitted zero velocity vertices, including with `object_static=1`. The failed forced-static experiment was stopped; it did not establish the original proposed cause.

Added captured-hand vertex/projection diagnostics, removed both skin/animation mods, and checked again. `no-mods-hand.json` and `no-mods-shaderless-hand.json` both record 48 captured, zero drawn vertices and a valid hand projection. The issue therefore also exists without those mods.

A temporary history-rejection diagnostic produced `hand-rejection.json`: 48 current and previous vertices, matching feature and signature, but `model=false`. The diagnostic string was removed from production after this check.

Minecraft's `OrderedSubmitNodeCollector.submitModelPart` constructs a fresh `Model.Simple` each submission. `AvatarRenderer.renderHand` uses that method. `Model.renderToBuffer` draws its persistent `root()` geometry. Comparing the wrapper reference therefore rejected valid arm history every frame. This is a source-level root cause supported by the live rejection check.

Fix: `motion/ObjectMotion.java:245` retains `model.model().root()` as geometry identity. This fixes every model submission using the shared path, including model-part callers outside the hand. Existing vertex-count, material/UV signature, topology, displacement and reset checks remain in force.

With copied skin/animation mods restored, `hand-root-fixed-forced.json` reports 104 captured and 104 drawn vertices with `object_static=1`. `root-fixed-pan.json` still reports 104 captured and zero drawn during the turn, whereas `root-fixed-force-pan.json` draws all 104. That isolates the second defect independently of wrapper identity: stationary eye-space geometry was skipped even though pack hand pixels retained world camera reprojection.

Fix: `motion/ObjectMotion.java:344` and `motion/ObjectVelocityPass.java:102` submit all hand quads with continuous history, including stationary ones. `handContinuous` still rejects nonfinite or teleport-sized discontinuities. The velocity shader retains the existing hand-depth equality test, so hidden faces do not write through visible surfaces. The world mask policy was not reversed or relaxed.

The selected first/last frames show the pig turning and changing pose; they do not establish a controlled, constant-speed walking route. These are exploratory reproduction views, not a matched motion-quality pass. No post-upscale name-tag option was added.

The 26.3 collector converts name tags into `TextFeatureRenderer.Submit` nodes. Both the normal depth-tested part and optional see-through part must be preserved. `ObjectMotion.IGNORED_TYPES` currently excludes text; world-space text therefore does not get the geometry velocity pass used by model surfaces. This is a verified coverage gap, not proof that adding object vectors alone repairs every glyph.

Rendering name tags after SR is a reasonable next implementation, but directly copying the particle/HUD paths would violate current contracts:

- `upscale/DeferredEffects.available` excludes shader packs and OIT.
- `UpscalingRenderer.java:667` resolves display depth only for pending effects or post effects needing depth. Pack captures here report `post_depth_resolved=false`.
- `FrameGenerationRenderer.captureUiAlpha` clears its depth to zero. Simply replaying world-space text there would remove the scene occlusion needed by the normal name-tag layer.
- The FG hudless capture is after scene effects. Drawing tags after SR but before that capture still includes them in FG scene interpolation.

A shipped solution needs display depth, the vanilla see-through split, removal from both SR and FG hudless scene inputs, and compositing the depth-tested coverage into the FG UI-alpha layer. That would repeat real-frame name-tag placement on generated frames, like the HUD, rather than interpolate glyphs. Pack and perspectivenametag compatibility and moving named-entity occlusion still require validation. No such solution is claimed implemented here.

Directly downloaded and read [NVIDIA's DLSS Programming Guide](https://github.com/NVIDIA/DLSS/blob/main/doc/DLSS_Programming_Guide_Release.pdf), dated 31 March 2026, PDF SHA256 `DCA4D2E68CCEDC04A431803595867A893474B1CCE033E65A41E9EAB9F6B436F8`. Local reference is `%TEMP%/rxA-reference/dlss.pdf`; extraction uses pypdf installed only in that temporary reference directory, not a project dependency.

Section 3.5 recommends native bias plus log2(render/display), minus one, plus content adjustment. It permits less aggressive bias for distracting aliasing, up to log2(render/display). Section 3.7.1 scales a base phase count of eight by the squared output/render ratio and lists 72 phases for Ultra Performance. The guide's prerequisites prefer at least 32 phases.

`upscale/DlssMath.java` implements those policies with a DLSS floor of 32. At actual 853/2560, ceil(8*(2560/853)^2) is 73; the bias is -2.585526. Quality is 32 phases and approximately -1.584681. `pack-up-before.json` records 6/6 `u_BlockTex` binds with the Ultra Performance bias. Pre-exposure is 1.0 and vendor auto exposure false in `hand-pan-before.json`.

The requested alternative already exists: `/set mip_bias_offset 1` changes Ultra Performance to approximately -1.585526. The existing key is finite-checked and runtime-only; adding another switch would be redundant. The measured sampler application and phase count do not establish an integration defect. Recommendation: retain offset zero pending repeated static and matched-pan tests with this exact pack and content. The lead should choose any default relaxation after those tests.
