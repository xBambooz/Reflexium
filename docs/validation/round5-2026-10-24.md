## Streamline DLSS-G

### What was added

- `native/reflexium_sl.cpp` loads `sl.dlss_g`, queries `numFramesToGenerateMax`, and exposes
  `slDLSSGSetOptions`, `slDLSSGGetState`, per-frame tag and clear calls, and the generated-present
  counter. DLSS-G reports max 6x (5 generated frames) on this GPU and driver.
- Each real frame tags display-resolution hudless colour, render-resolution depth and motion vectors,
  and a UI alpha buffer. UI alpha is preferred over UI colour plus alpha so the plugin derives UI
  colour from final and hudless; that keeps invert blends such as the vanilla crosshair correct.
- Minecraft's final swapchain blit mirrors Y. DLSS-G composes directly into that backbuffer, so
  hudless, depth, motion and UI alpha are mirrored into the same orientation. Motion-vector Y uses a
  negative `mvecScale`, jitter Y is negated, and the clip matrices use `F * M * F` with
  `F = diag(1, -1, 1, 1)`. A depth flip uses the existing depth-resolve shader with a mirror flag.
- Menus, pause, loading and missing world frames set DLSS-G off with `eRetainResourcesWhenOff`.
  A fixed 2x/3x/4x maps to `numFramesToGenerate` 1/2/3. Auto stays the application policy because
  Streamline Dynamic MFG is D3D12-only at 2.14.16.
- DLSS SR and DLSS-G cannot share Streamline's one per-frame constants block with different Y
  orientations. The supported resolution is: when Streamline FG is active, SR runs on the raw NGX
  feature and DLSS-G owns the Streamline constants. With FG off, SR uses Streamline.

### Focus behaviour

NVIDIA's `sl.common` imports `GetForegroundWindow` and DLSS-G disables interpolation while the
application window is not focused. The pinned guide documents no option to keep generating in a
visible but unfocused window. The integration therefore keeps the game rendering, leaves the
options and tags valid, and reports the pause:

```
Frame generation: DLSS FG 2x (Streamline) (window unfocused: DLSS-G paused by NVIDIA)
```

The test frame stayed unfocused on purpose, so every run reported the pause, no generated presents,
no failed tag or option call, no Streamline warning, and continuous real presents. A focused run is
required for the generated-frame counts and image captures; the options, tags and fallback are
verified unfocused.

## Objective 1: BSL forest 1440p

Per-pass GPU means in microseconds, same pose (200.5, 67, 150, yaw 90), 4.5 s windows.

| Span | Native | DLSS Quality |
| --- | ---: | ---: |
| World (includes children) | 5522.5 | 6257.0 |
| DLSS evaluate | 0 | 531.8 |
| Camera motion | 0 | 34.2 |
| Iris shadows and prepare | 1471.4 | 1240.7 |
| Iris deferred | 832.6 | 358.2 |
| Iris composite | 880.2 | 483.6 |
| Iris final | 101.8 | 24.8 |
| Terrain solid | 1839.9 | 3162.9 |
| Final blit | 18.1 | 28.1 |

The pack's deferred and composite passes shrink as expected. Terrain solid grows by 1.32 ms at the
lower render size. The following A/Bs tested the hypotheses:

| Change | World GPU | Terrain solid GPU | Shadow GPU |
| --- | ---: | ---: | ---: |
| Quality, default | 6156 | 2999 | 1178 |
| `mip_bias_offset=+1` | 6377 | 3036 | 1425 |
| `mip_bias_offset=+2` | 6212 | 2959 | 1241 |
| Quality, jitter off | 6217 | 3162 | 1148 |
| `pack_shadow_cap=1024,128` | 4499 | 2040 | 410 |
| `pack_shadow_cap=2048,128` | 3990 | 1900 | 258 |
| `pack_shadow_cap=0,128` (pack resolution, 128 distance) | 4148 | 1900 | 348 |

The mip bias and jitter are not the cause. The cost follows the pack's shadow distance: keeping the
pack's own shadow map resolution but limiting shadow distance to 128 blocks recovers terrain solid
from 3162.9 to 1900 us and the world from 6217 to 4148 us. This is BSL's shadow filtering cost at the
lower screen resolution, not a Reflexium pass. The existing opt-in `pack_shadow_cap` exposes the
trade; the default keeps the pack's saved shadows, so the 1440p Quality loss remains.

## Objective 1: shaderless overhead floor

Shaderless 1080p range, native versus DLSS Performance, per-pass means.

| Span | Native CPU / GPU | Performance CPU / GPU |
| --- | ---: | ---: |
| World (includes children) | 584 / 1901 us | 746 / 1897 us |
| DLSS evaluate | 0 | 101 / 353 us |
| Camera motion | 0 | 6.7 / 18.7 us |
| Object motion | 0 | 12.1 / 0 us |
| Display-depth resolve | 0 | 8.1 / 37.5 us |
| Barriers before/after | 0 | 1.5 / 5.0 us |
| Final blit | 4.5 / 13.1 us | 3.2 / 12.6 us |

The world GPU time is unchanged at the lower render size because this scene is geometry bound. The
DLSS path adds 353 us of evaluation, 37.5 us of display-depth resolve when post effects sample depth,
and about 25 us of motion and barrier work. CPU adds 101 us of evaluation, 19 us of motion and 8 us of
depth. All of those are required inputs or the vendor evaluation; no removable Reflexium pass was
found. That is the honest floor, and it explains why Performance is neutral and Quality loses in
this scene.

## Reflex and PCL latency

Shaderless 1080p range, Streamline SR path, frame generation off, uncapped:

| Reflex mode | FPS (2 runs) | Delta |
| --- | ---: | ---: |
| Off | 480.7 / 479.5 | - |
| On | 476.9 / 483.0 | about 0% |
| On + Boost | 478.2 / 479.9 | about 0% |

The Streamline sleep cost is negligible. `slReflexGetState` reports `lowLatencyAvailable=true` and
`latencyReportAvailable=true`, but the 64-entry `frameReport` is empty, so `reflex_timings` returns
no frames and the F3 line says "waiting for Streamline data". Setting the supported
`ReflexOptions::useMarkersToOptimize` did not populate it, so it was reverted. A PCL stats message
reader is not implemented. This is an open gap, not a pass.

The same scene on the raw low-latency2 path is readable:

| Reflex mode | FPS | Delta | Render latency |
| --- | ---: | ---: | ---: |
| Off | 555.9 | - | 3.2 ms (submit 1.8, GPU 2.3) |
| On | 483.8 | -13.0% | 2.7 ms (submit 1.0, GPU 1.7) |
| On + Boost | 485.2 | -12.7% | 3.3 ms (submit 1.6, GPU 2.4) |

Reflex On cuts measured latency by 0.5 ms, but not without a meaningful FPS loss on the shipping raw
path. The Streamline path has the cost behaviour the objective wants and no readable latency proof.

## DLSS-G output format and banding

The Vulkan surface offers `VK_FORMAT_A2B10G10R10_UNORM_PACK32` (format 64). The swapchain now selects
it when Streamline is initialized and frame generation is an NVIDIA mode; `-Dreflexium.tenBit=true`
forces it for other tests. Verified swapchain format 64 at 1920x1080 with BSL and DLSS Performance,
with no present or blit error.

Same-frame real sky at 1920x1080, BSL, DLSS Performance, 500x260 crop:

| Image | Flat pixel fraction | Distinct luma levels |
| --- | ---: | ---: |
| 8-bit main render target (harness capture) | 0.660 | 82 |
| 10-bit presented frame (desktop capture) | 0.679 | 83 |

The real frame's dither is not destroyed by the 8-bit to 10-bit presentation path. DLSS-G generated
frames cannot be captured from the harness render target, and the window was unfocused, so the
generated-frame flat fraction (previous raw-path reference 0.567 versus 0.396 real) was not
remeasured on Streamline. The generated-frame half of objective 5 remains open and needs the focused
run.

## Distant Horizons LOD mip bias

DH binds its LOD block atlas through its own Blaze render pass, outside the shared material binding
boundary. A `@WrapOperation` on `RenderPassWrapper.bindTexture` now replaces the DH sampler with the
same `log2(renderWidth/displayWidth) - 1` bias used for Sodium and vanilla terrain. The replacement is
owned and closed by the existing sampler cache, and non-mipmapped DH textures are returned unchanged.

At the forest pose, shaderless, DLSS Performance at 1080p, the status recorded 59 DH atlas binds, all
with the requested -2.0 bias. With BSL the DH terrain uses the Iris DH path and its material sampler
instead. A far-LOD gradient A/B against native could not run because this save is still generating
Distant Horizons LOD data (2.9 to 3.1 million chunks left, ETA hours). The hook is structurally
verified; the far-LOD image metric is not.
