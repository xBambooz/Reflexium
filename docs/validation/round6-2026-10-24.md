# Round 6: clean load, BSL shadow cost, Streamline by default and the validated matrix, 2026-10-24

This round removed the background Distant Horizons load from every frame-rate measurement, bounded the
BSL shadow cost that grows when the viewport shrinks, made Streamline the default path, fixed four
gating bugs found by the measurements, and re-ran the release matrix with the measurement-validity
proof required by [OBJECTIVES.md](../OBJECTIVES.md). Objective 6 was added while the round was running;
its audit is section 7.

## Environment and method

- Windows 11, RTX 5070 12 GB, NVIDIA 617.42, GraalVM Java 25.0.4, Minecraft 26.3, Vulkan backend.
- Streamline 2.14.16 is the default path this round. `-Dreflexium.streamline=false` selects the raw
  NGX fallback. The raw rows below say so explicitly.
- Harness window 1920x1080 on the secondary XF250Q 240 Hz display; 1440p and 4K rows resize the
  swapchain in place. Present mode IMMEDIATE, VSync off, Max Framerate 260 (Unlimited).
- Iris `1.12.0-snapshot+mc26.3-local`, BSL v10.1.8, Complementary Reimagined r5.9.3, Solas,
  Mellow v3.4.1a, Sodium 0.9.2. Render distance 31, simulation distance 12, sound muted.
- **Distant Horizons was removed from `run/mods`** for every measurement. Round 5's numbers were taken
  while DH was generating about 3 million LOD chunks in the background. The clean load is verified in
  section 1.
- From 06:19 the desktop was covered by the user's black always-on-top OLED-care overlay
  (`tools/oled-overlay.ps1`, left running untouched). The validated matrix ran under it. An A/B taken
  immediately before and after the overlay appeared shows no effect: BSL 1080p range native 322.9 FPS
  with the overlay versus 321.5 FPS before, and DLSS Performance 336.2 versus 334.6 FPS. Render-target
  screenshots still work and are used as content proof (mean luma 152, variance 2697 on a sample).
- Every matrix row was measured twice back to back. The tables show the mean of the two samples only
  when they agree within 3%; the largest difference observed was 1.4%.

## 1. Clean load and the round 3 baseline row

Distant Horizons was moved from `run/mods` to `run/mods-off` before the first launch. With the title

## 2. The BSL terrain cost that grows at a smaller viewport

The round 5 symptom reproduced with the pack's own shadow settings at 1440p forest: native terrain
solid 817 us, DLSS Quality 1611 us, Quality 14.6% slower. Each change below was measured on its own
launch or pack reload at the same pose (200.5, 67, 150, yaw 90).

| Change | Native FPS | Quality FPS | Terrain native | Terrain Quality | Shadow native / Quality |
| --- | ---: | ---: | ---: | ---: | ---: |
| Pack defaults (2048/256) | 281.2 | 240.2 (-14.6%) | 817 | 1611 | 957 / 909 |
| `SHADOW=false` | 404.8 | 432.0 (+6.7%) | 758 | 812 | 0 / 0 |
| `SHADOW_COLOR=false` | 282.0 | 251.9 (-10.7%) | 778 | 1407 | 980 / 941 |
| `SHADOW_FILTER=false`, `SHADOW_COLOR=false` | 281.9 | 254.4 (-9.8%) | 765 | 1396 | 988 / 921 |
| `maxAnisotropyBit=0` | 275.6 | 240.6 (-12.7%) | 797 | 1599 | 977 / 909 |
| `mip_bias_offset=+1` (round 5) | not run | 240.7 | not run | 3036 | not run |
| `jitter=false` (round 5) | not run | 240.7 | not run | 3162 | not run |

The growth disappears only with shadows off. It survives removing the colour taps, the 9-tap filter,
anisotropy, the material mip bias and jitter. It also appears in native alone when the window is
smaller:

| Native window | FPS | Terrain | Shadows |
| --- | ---: | ---: | ---: |
| 3840x2160 | 171.8 | 1172 | 1047 |
| 2560x1440 | 280.0 | 833 | 1009 |
| 1920x1080 | 268.3 | 1540 | 993 |
| 1707x960 | 285.9 | 1401 | 1013 |
| 1280x720 | 327.2 | 1071 | 888 |

That rules out the upscaler: the cost follows the viewport, not the DLSS state. Checked and excluded on
the Reflexium side:

- The material mip bias reaches only `Sampler0`, `u_BlockTex`, `pack_atlas`, `pack_pbr` and
  `dh_atlas`, all color textures with more than one mip. It never reaches the shadow map, depth, noise
  or pack LUT bindings.
- Jitter and anisotropy changes have no effect.
- The shadow map is Iris's square `ShadowRenderTargets.resolution` from the pack option, not a
  render-size target.
- Reflexium's own passes do not grow: `evaluate` is 0 native and about 415 us at Quality,
  `display_depth` is 0 in this scene, and the final blit is unchanged.

The terrain-phase span grows even with a single shadow tap per pixel, which tap count cannot explain.
The remaining candidate is inside Iris/BSL (timestamp attribution or shadow-fetch cost at the smaller
viewport). That is not proven and is an open item, not a Reflexium pass.

### Shadow caps removed

`pack_shadow_cap` is deleted from config, persistence, the pack-option override, the debug key, the
Video Settings and Sodium controls, the two option enums and the lang keys. It was a workaround with no
root cause, and it leaked: BSL wrote the capped effective values back to
`shaderpacks/BSL_v10.1.8.zip.txt` on reload/exit (observed `1024,128` after round 5). The pack now owns
its shadow settings; this report uses the pack defaults 2048/256.

## 3. Streamline as the default path

Streamline is now enabled unless `-Dreflexium.streamline=false` is set. Bugs found and fixed while
measuring:

1. `configuredGeneratedCount` ran after `refreshPolicy.bypass()`, and the policy was never configured
   before that gate, so a fixed 2x/3x/4x could never enable FG. The count is now computed first; fixed
   multipliers bypass the output budget; Auto keeps the refresh-headroom policy.
2. `fg_force_multiplier` is removed. A fixed multiplier is intrinsically the user's request.
3. `set shader_pack <name>` stored a name without `.zip`, which made Iris fail every later load
   ("Pack is not valid") until `iris.properties` was repaired. The dev helper now resolves the file name.
4. `VK_SUBOPTIMAL_KHR` was treated as a failure after every present, which called `invalidate()` and
   toggled DLSS-G off and on every frame (measured 124 resets/s). SUBOPTIMAL delivers the image and is
   now accepted. This removed the per-frame toggling.
5. The swapchain/present proxies were resolved through the interposer's `vkGetDeviceProcAddr`. They now
   prefer the interposer's own exports, with a logged note when the two pointers differ.

Streamline versus the raw NGX fallback (different launches, same tree and pack):

| Row | Raw NGX | Streamline |
| --- | ---: | ---: |
| BSL 4K range native | 174.2 | 159.3 |
| BSL 4K range Quality | 156.0 | 199.9 |
| BSL 1440p forest native | 278.5 | 281.1 |
| BSL 1440p forest Quality | 240.7 | 240.3 |

Streamline SR matches raw at 1440p Quality and is clearly faster at 4K Quality, but native is 8.6%
lower on the Streamline launch at 4K. The raw path therefore stays as the fallback.

**Not done: one constants block for SR and DLSS-G.** Minecraft's present blit mirrors Y, so the
presented backbuffer and the scene have opposite orientations, and Streamline accepts one
`sl::Constants` per frame. Unifying them needs either a whole-frame orientation change (world
projection, motion vectors, GUI projection and the present blit) or a display-size flip of SR's output
plus flipped SR inputs, which adds about 0.15 ms per frame and worsens the shaderless deficit. SR still
uses raw NGX while Streamline FG is active; with FG off it uses Streamline.

| Scene | Off | On | On + Boost |
| --- | ---: | ---: | ---: |
| 1920x1080, FPS | 1427.6 | 1422.6 (-0.35%) | 1415.5 (-0.85%) |

The sleep cost is negligible. The latency proof is missing: `reflex_timings` returned zero frames in

`sl_reflex.h` marks `frameReport` valid only when `latencyReportAvailable` is true; Streamline reports

## 5. DLSS-G: what was found and why generated frames are still missing

Focus was granted for this round and used before the OLED overlay appeared:

| Window | Start | End | Duration | Foreground restored |
| --- | --- | --- | ---: | --- |
| 1 | 2026-10-24T04:59:48 | 2026-10-24T05:01:24 | 96.7 s | yes |
| 2 | 2026-10-24T05:11:46 | 2026-10-24T05:12:55 | 68.9 s | yes |

Total focused time was 2 min 46 s. In both windows `GetForegroundWindow` equalled the game HWND. The
generated-present count stayed 0 at effective multipliers 2, 3 and 4. The `VK_SUBOPTIMAL_KHR`
invalidation bug above was found in this test and fixed, which stopped the per-frame off/on toggling,
but it did not produce frames.

After the overlay appeared, focus was no longer taken (per the user's instruction), and the plugin was
probed without it. Current state with FG requested at 2x:

| Field | Value |
| --- | --- |
| `fg_effective_multiplier` | 2 |
| `slDLSSGSetOptions` | applied once, mode 1, generated 1, UI true |
| `slDLSSGGetState` | `numFramesToGenerateMax` 5, `status` 0, `numFramesActuallyPresented` 0, minimum dimension 100 |
| `fg_streamline_present_result` | 0 (`VK_SUCCESS`) |
| generated presents | 0 over 10 s |
| Reflex | On, sleeping, latency report unavailable |

What was excluded:

- The multiplier/options path: options are applied and stable; no OFF/ON toggling remains.
- The minimum size: the backbuffer is 1920x1080, far above the reported minimum 100.
- The present result: `VK_SUCCESS`.
- The swapchain recreation rule (DLSS-G guide 18.0): a resize while FG was on recreated the swapchain
  (log: "Swapchain created ... 1920x1070" then "1920x1080") and still produced 0.
- The interposer proxy: present/acquire/create now resolve from the interposer's exported symbols.
- `sl.common.dll` imports `GetForegroundWindow` and `GetWindowThreadProcessId` only (no
  `GetActiveWindow`/`GetFocus`), so the documented unfocused pause is the last external gate. The test
  window is created non-focusable by the harness and only ever became foreground, never an activated
  window; after the overlay appeared it cannot be made foreground at all.

This is reported as a blocker, not a product failure: a normally launched client with an active window
is the missing test. The two code fixes above are required for that test to have any chance of working.
The next actions are (a) run a normally launched client with FG on, (b) call `slSetFeatureLoaded` and
recreate the swapchain around the DLSS-G on/off transition as the guide requires, (c) move
`slDLSSGGetState` to a present-thread-safe point.

### Shaderless overhead under the 2% rule

Shaderless 1080p range per-pass means, current build:

| Span | Native GPU / CPU | Performance GPU / CPU |
| --- | ---: | ---: |
| World (includes children) | 485 / 174 us | 788 / 316 us |
| DLSS evaluate | 0 | 264 / 71 us |
| Camera motion | 0 | 30 / 9 us |
| Object motion | 0 | 7.5 / 28 us |
| Display-depth resolve | 0 | 25 / 5 us |
| Barriers | 0 | 3.4 / 1 us |
| Final blit | 12.5 / 3.3 us | 13 / 2.3 us |

The added frame time is about 307 us (1518 to 1035 FPS). 264 us is the vendor DLSS evaluation; the
removable Reflexium work is about 66 us GPU and 42 us CPU. Even removing all of it would leave a 25%
gap at this scene, not 2%. The 2% rule cannot be met on a 0.66 ms frame where the vendor evaluation is
a serialized 0.26 ms pass. The tooltip recommendation is in place ("Recommended: Off (or Auto) when not
using a shader pack..."). The measured gap is reported honestly: 32.1% to 38.9% at 1080p, 39.5% to
45.5% at 1440p, 49.5% to 56.0% at 4K.
