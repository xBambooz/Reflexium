# Voxy LOD DLSS test, 2026-10-24

Plan: [specs/VOXY_LOD_DLSS_PLAN.md](../specs/VOXY_LOD_DLSS_PLAN.md). Objective:
[OBJECTIVES.md](../OBJECTIVES.md) objective 1. This round tested whether LOD terrain makes the
shaderless Vulkan path GPU bound enough for DLSS to pay for itself. Voxy failed Gate 0 on the
Vulkan backend, so the run continued with Distant Horizons 3.3.5-dev as the plan's fallback LOD
source.

Result: **objective 1 for the LOD scenario fails.** With LOD at 256 chunks, every DLSS mode loses
at 1440p. At 4K only Performance wins, by 4.2 to 6.6 percent on the two vista scenes, while Quality
loses 3.1 to 9.8 percent and Balanced ranges from -6.4 to +1.7 percent. No LOD ghosting or seam
shimmer was found. The in-game tooltip and README were not changed because the plan's pass criteria
are not met.

### 0.2 Voxy on Vulkan: fail

Voxy was installed alongside the existing Sodium, Fabric API and Distant Horizons, with Iris
removed because Voxy declares it incompatible. The client started and then logged:

```text
[Render thread/ERROR] (Minecraft) Failed to create backend Vulkan
com.mojang.renderpearl.api.device.BackendCreationException: Voxy does not presently support vulkan
    at knot//net.minecraft.client.Minecraft.wrapOperation$bed000$voxy$forceOpenglDevice(Minecraft.java:7692)
[Render thread/INFO] (Minecraft) Using graphics backend OpenGL, using drivers: 3.3.0 NVIDIA 617.42
```

The jar also contains a full OpenGL abstraction (`me.cortex.voxy.client.core.gl.*`). Voxy forces
OpenGL before Reflexium can attach to a Vulkan device, so Reflexium reported
`upscaling_active=false` and `Upscaling: needs the Vulkan renderer`. Voxy was removed from
`run/mods` and is not kept. Gate 0 stops for Voxy and continues with the plan's DH substitute.

### 0.3 Distant Horizons substitute on Vulkan: pass

With DH restored, the same launch reports:

```text
Using graphics backend Vulkan, using drivers: 1.4.351 NVIDIA 617.42
DH rendering definition bound to: [Blaze3D: VULKAN]-[VULKAN], name: [BLAZE_3D]
```

Reflexium upscaling is active, `primary_depth_source=vanilla_world`, and the camera history far
plane is DH's `13033.393` (the main near plane is preserved and extended). DH depth is
`D32_FLOAT` at the render size. During initial 256-chunk LOD streaming, 140,553 DLSS evaluations
reported `history_reset_frames=1` with reason `feature rebuild`; no resets came from streaming.

LOD coverage and settings used for the measurements:

- LOD radius 256, then 512 chunks. DH rewrote a requested 128 to 256 while
  `realTimeUpdateDistanceRadiusInChunks` was 256, so both keys were set together for the later
  runs.
- DH quality `MEDIUM`/`MEDIUM`, transparency `COMPLETE`, anti-aliasing off. DH rewrote HIGH to

- The initial dense generation pass was limited to the already generated core; the outer radius
  was generated surface-only (`surfaceRegenMaxDistancePercent = "0.0"`) so the dataset could be

  a dense core inside 256 and surface-only terrain outside it.
- The generated DH database is 622 MB at
  `run/saves/Reflexium Vitrail Smoke/dimensions/minecraft/overworld/data/DistantHorizons.sqlite`.

### 0.4 Depth, motion, jitter and mip-bias coverage

| Requirement | Result | Evidence |
| --- | --- | --- |
| Jitter shared with near terrain | **Pass** | DH's `MixinProjectionMatrixBufferCommon.onMatrixWrite` captures the matrix written to `ProjectionMatrixBuffer.getBuffer`. Reflexium's `GameRendererMixin.reflexium$jitterLevel` is a `@ModifyArg` on that same call, so DH receives the jittered matrix. |
| LOD depth merged for DLSS | **Pass** | `BlazeDhTerrainMixin` calls `DistantHorizonsCompat.captureNative` after DH terrain; reverse-Z `D32_FLOAT`; `depthTransform` extends the near plane's reverse-Z far plane; the motion pass merges the DH frame. |
| Camera motion for static LOD | **Pass** | Camera-only vectors come from the same matrices and merged depth in the motion pass. No separate LOD heuristic exists. |
| Same negative mip bias on LOD textures | **Fail** | Reflexium's bias is applied at `FrontendRenderPass.setUniform` material binds and in the `VulkanGpuSampler` bias window. DH binds its own `BlazeBlockTextureAtlas` sampler and passes through neither hook. LOD textures therefore keep their neutral bias. |
| No history reset on LOD rebuilds | **Pass** | No reset is requested by DH streaming. Observed resets were `feature rebuild` and `teleport` only. |

The mip-bias miss is recorded, not patched. Fixing it means hooking DH's sampler creation, which is
a separate integration item and was out of scope for this measurement round.

## Gate 1: integration

The four plumbing requirements pass in code and in the live client, including the jitter path that
matters most for LOD shimmer. The missing LOD mip bias is the one integration gap. No band-aid path
was added.

## Gate 2: measurement matrix

### Protocol and the warm-up problem

The first automated pass used two 2.5 s samples per cell immediately after each setting change. That
protocol is not usable for DH: after a camera teleport, DH's LOD quadtree takes tens of seconds to
reach steady state, and the native row, which is measured first, absorbs the load. On the 512
vista the same pose read 42 FPS early, 178 FPS after about two minutes, and 323 FPS when settled.
The initial 120-row matrices at 256 and 512 are committed as raw evidence but are not used for the
verdict.

The verdict uses a paired protocol: a 45 s scene settle, then native and each DLSS mode alternating
for two cycles, 4.5 s after each mode switch, 2.5 s sample windows. Alternating cancels the slow
drift that remains. The 512 rows use a 60 s settle and three samples. Each number below is the mean
of the repeated samples in the committed CSV. Spreads above 3 percent are named in the text.

FPS is the render-thread frame-stamp mean from `frame_mark` and `frame_stats_from`. These are
application counters, not scanout.

## Gate 3: image quality with LOD

Native versus DLSS at 1080p, range vista, 256 chunks. All crops are at or below 960 px.

- Static: the 480x270 far-LOD crops (`crop-far-native.png`, `crop-far-p.png`) show the same
  mountains, forest, water and smoke platform. Over the LOD band the native-to-DLSS PSNR is 30.1 to
  30.3 dB. Mean luma gradient is 14.4 native and 11.8 to 11.9 for Quality/Performance, a ratio of
  about 0.82. The LOD terrain is slightly softer under DLSS, consistent with temporal
  reconstruction; no detail is missing from the inspected crops.
- Slow pan, DLSS Performance: 90 degrees over 60 ticks, 8 frames at 80 ms, yaw 0 to 75. No ghost
  trail behind gates, fences or clouds, no bar or chain doubling, no LOD edge shimmer.
- Fast flick, DLSS Performance: 120 degrees over 8 ticks. The turn happened between frames 0 and 1
  (yaw 7.5 to 127.5), the known `capture_sequence` limit. The reset frame is clean with no smear
  or duplicated gate edges.
- Walk with view bob, DLSS Performance: 6 frames, z 0.5 to 4.8, bob 0 to 0.1. The lane texture,
  gates and the LOD band stay single-edged; no smear.
- Moving mobs: horse, pig and cow in the pen at native and DLSS Performance. No doubled legs or
  heads in the inspected frames. The captures are not simultaneous, so this is a per-frame check,
  not a matched object-vector test.
- DH's own LOD defects, present in native and DLSS alike: staircase chunk seams on distant slopes
  and one flat white LOD quad near the smoke platform. Neither is a Reflexium artifact.

No LOD ghosting or seam shimmer was found, so the image-quality half of the pass criteria holds.
The performance half does not.

## Pass or fail

Plan criteria: with LOD at 256 chunks or more, DLSS Quality, Balanced and Performance must beat
native at 1440p and 4K without shaders, with no LOD ghosting or shimmer.

**Fail.** At 256 chunks, 1440p, all three modes lose in all four scenes (Quality 8.0 to 10.7
percent, Balanced 3.3 to 6.6 percent, Performance 0.7 to 4.4 percent). At 4K, Quality loses in
every scene, Balanced is roughly neutral at best, and Performance gains on the range forward and
vista scenes (+6.6 and +4.2 percent); the platform cell reads +1.4 percent but is unstable. The
512-chunk rows repeat the pattern. The measured floor
is the DLSS evaluate cost: about 1.3 ms at 4K against a 1.8 ms fill saving in this LOD scene.

Objective 1 for the LOD scenario is not met. The recommendation stays Off or Auto without shaders,
so `reflexium.option.upscaler.tooltip` and the README were not changed.

## Streamline spot check: not run at measurement time

The default raw NGX path was measured. The planned Streamline spot check was attempted at 02:41 and
blocked by the bridge state present then:

- With `-Dreflexium.streamline=true` the client logged
  `Could not load the Streamline bridge, Streamline is unavailable` and
  `java.lang.IllegalStateException: missing export rx_sl_dlssg_available`
  (`StreamlineBridge.java:365`, first lookup at line 79).
- The `reflexium_sl.dll` copies present at that time (`run/reflexium/natives`,
  `src/client/resources/natives`, `build/resources/client/natives`) had SHA-256
  `98A0AAE71855BB2042DCA4D70F49C05758070F7A039DAF7F5A23FE1CC136F9A7` and exported no `rx_sl_dlssg*`
  symbol.
- `native/build.cmd` rebuilt `reflexium_ngx.dll` but failed on the Streamline bridge:
  `native\reflexium_sl.cpp(388): error C2589: '(': illegal token on right side of '::'` and
  `error C2059: syntax error: ')'`. The three lines are `std::max(...)` calls that collide with
  the `windows.h` `max` macro.

A concurrent Streamline agent was working in the same checkout. It rebuilt `reflexium_sl.dll` at
02:50 with the DLSSG exports and changed the Java binding, so the block above is time-scoped. The
spot check was not rerun against that in-progress work: running a second client and build on the
shared checkout would have collided with it. The raw-path matrix and verdict are unaffected. This
is a working-tree state, not a Reflexium LOD behavior result.

## Limits

- Voxy itself was never measurable on Vulkan. Its LOD geometry, fill cost and shader path are
  untested by design of the blocker.
- DH quality was MEDIUM/MEDIUM with COMPLETE transparency. DH rewrote HIGH to MEDIUM at load on
  this build. A higher quality preset would add fill work and could move the 4K numbers; it was not
  reachable through the config on this build.
- The 512 dataset has surface-only terrain outside the 256 core. The verdict uses 256 as the
  primary row, which meets the plan's "256 chunks or more" bar with a fully settled dataset.
- The full 120-row matrices at 256 and 512 are committed but were taken with the earlier protocol
  and are not suitable for percent deltas. They are listed for completeness.
- No shader pack was tested with LOD. The plan's scenario is shaderless.
- The 4K platform cell and the 1440p 512 forward native pair have spreads above 3 percent and are
  flagged rather than repeated to convergence.
- A concurrent Streamline agent shared this checkout. Its client launch and native rebuild at 02:49
  postdate the measured windows, and the paired rows repeated within 2 percent, but a hidden
  shared-GPU load would affect native and DLSS rows alike rather than one mode.

Then join `Reflexium Vitrail Smoke`, run `/function reflexium:build_range` and
`/function reflexium:spawn_mobs`, set the DH keys above, and use the poses:
